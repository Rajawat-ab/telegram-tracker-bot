Reliability

What happens when something breaks

Two rules carry most of the weight. A message is only confirmed after its data is pushed, and state.json records the last handled update id, so anything at or below it is never processed again.

If this failsWhat happensHow it recovers
The relay can't start a run (token expired)The message waits in the inbox with 👀The 2-hour backup run picks it up
Telegram or the relay is unreachable at pre-checkThe run goes red and GitHub emails youThe next run retries; messages keep waiting
The R step crashesNo commit, no replies, no confirmationThe next run processes the same messages
The push is rejectedPulls, rebases and retries up to 3 timesIf it still fails, nothing was replied to, so the retry is clean
A reply fails to sendThe data is already savedMessage is confirmed; only the reply is lost
The same message arrives twiceInbox dedupes by id; R skips ids at or below the watermarkNever logged twice, /undo never repeats
A stranger messages the botThe relay drops it at the edgeNever reaches GitHub or uses minutes
Two runs start togetherOne concurrency group: one runs, the rest queueQueued runs collapse into one
Scheduled messages

Nudges and recaps can't be missed

Every run, whatever started it, checks whether a report is due and not yet sent today. The 9 pm habit nudge stays quiet when everything is done; the Sunday 8 pm recap sends a text summary and two charts drawn with ggplot2. The dates they went out are stored in state.json, so a late or skipped schedule only delays a report, it never loses or repeats one.

Deploying the relay

One button in the Actions tab

  1. Check all six secrets are present and the relay secret is strong.
  2. Deploy the Worker and its Durable Object inbox with Wrangler.
  3. Upload the Worker's four secrets.
  4. Point the Telegram bot at the relay (setWebhook with the secret header).
  5. Fire a test run once RELAY_URL is set.
  6. Print the relay URL in the run summary.
